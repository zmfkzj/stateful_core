# Stateful Command Policy

This skill is the procedural manual. Rules decide when Stateful policy applies; this file explains how to satisfy that policy without probing through Bash, bypassing hooks, or widening write scope.

## Skill Authoring Boundary

This skill may teach agents how to use `stateful` correctly: inspect current state, declare reservation, acquire and release claims, claim reservations, choose sandbox profiles, and recover from hook denials. Do not add benchmark-specific success strategies, direct orchestration plans, role assignments, or mandates for how main agents and subagents should divide domain work. Work-allocation guidance belongs here only when it is necessary to avoid `stateful` coordination errors such as overlapping claims, shared scratch paths, stale reservations, or same-session claim denials.

Benchmark prompts must not be injected through this skill except for instructions that are explicitly part of testing concurrent-work behavior. The skill must not try to improve benchmark patch quality by telling agents which domain roles to spawn, which files to assign, or which non-stateful task strategy to follow.

## Role Split With Rules

- Rules own activation: short always-apply or TTSR guidance tells agents when to consult this skill.
- This skill owns procedure: exact MCP flow, sandbox profile selection, denial recovery, and edge cases.
- Hooks own enforcement: hook allow means proceed; hook deny or unavailable means stop and choose the documented alternative.

## Default Write Flow

- First inspect current state with canonical Stateful MCP tool names: `state_context_render` or `state_current_read`. Confirm who is active, what this session already holds, pending reservations, and likely conflicts before choosing files, commands, or subagent work.
- Use canonical Stateful MCP tool names in guidance and reasoning: `state_context_render`, `state_current_read`, `state_session_register`, `state_reservation_declare`, `state_claim_acquire`, `state_reservation_request`, `state_notifications_poll`, `state_resume_next`, and `state_reservation_claim`.
- If the active tool list exposes only runtime-specific tool names, call the exact shown equivalent: Codex may expose `mcp__stateful__state_current_read`-style names and OMP may expose `mcp__stateful_state_current_read`-style names. Treat those wrappers as host-specific aliases for the canonical `state_*` tools, not as the canonical API.
- In OMP, if Stateful MCP tools are not in the active tool list yet, use `search_tool_bm25` once with a query such as `stateful state current read` to activate the installed stateful MCP tools, then call the activated runtime-specific tool names. Do not fall back to Bash for stateful coordination.
- Declare a task-level reservation with the full known file set using `state_reservation_declare(purpose=<task purpose>, files_planned=[...])`, then acquire same-session claims for the known write targets with `state_claim_acquire(paths=[...])` when more than one path is needed. Use a one-item `paths` list for a single target when available; legacy `path=...` acquire requests remain accepted for single-target compatibility. Expand the same task reservation with another declaration when the target set grows. Do not run `stateful reservation declare` or `stateful mcp call` through Bash.
- Codex installation writes `skills/stateful-command-policy/SKILL.md` and `skills/dispatching-parallel-agents/SKILL.md`; installed Codex config auto-approves Stateful MCP tools, but prompts for `stateful sandbox run --fs external --purpose ...` through Codex execpolicy rules. Treat that prompt as the approval boundary for validating any declared absolute repo-external write/create/directory/socket/signal scope, any repo-relative write/create/directory scope that also requires matching Stateful reservation and same-session claims, or a no-target external operation that is read-only apart from normal process execution.
- OMP installs the stateful integration into the live OMP profile agent directory (default `~/.omp/profiles/stateful/agent`, or the explicit OMP agent directory passed to install) with the stateful extension, an always-apply `rules/stateful-required.md` rule, this `skills/stateful-command-policy/SKILL.md` manual, `skills/dispatching-parallel-agents/SKILL.md`, and the `sandbox_bash`, `ext_ro_bash`, and `ext_rw_bash` custom tools. It merges an existing `config.yml` instead of replacing it and rejects invalid YAML. Without `stateful install --agent omp --update`, existing OMP scalar config values are preserved and only missing Stateful keys are inserted; with `--update`, the installer overwrites the targeted OMP scalar values to `tools.approvalMode: yolo`, `stateful.autoApprove: false`, `eval.py: false`, `eval.js: false`, `eval.rb: false`, `eval.jl: false`, and `bash.enabled: false`. The installer removes `tools.approval` from the stateful profile because yolo mode delegates safety to Stateful hooks while raw Bash/eval denials and sandbox tool confirmations remain hook-enforced.
- Raw OMP Bash and Python/JavaScript/JS/Ruby/Julia eval tools are denied by Stateful hooks before command text matters, so wrapping `stateful sandbox run ...` inside raw Bash or an eval tool is still blocked. OMP supports stateful `session-start`, `pre-tool-use`, `post-tool-use`, and `stop` hook lifecycles, but not `user-prompt-submit`. For non-external sandbox command work, use `sandbox_bash`. For external shell work, use `ext_ro_bash` for read-only commands with only `purpose` and `command`; it runs immediately without OMP UI confirmation. `ext_rw_bash` prompts for a scoped OMP UI grant unless `stateful.autoApprove: true` or per-call `auto_approve: true` is set; auto-approval skips only the Stateful-owned UI prompt and does not bypass Stateful sandbox scope validation, hooks, reservation/claim checks, or grant limits. Its approval shows the purpose, declared write/socket/signal scope, network mode, example command classes, max uses, and expiry instead of showing the raw command text. Later calls with the same approved purpose and scope can run without another prompt until the grant reaches its max uses or expires. When auto-approval is enabled, no prompt is shown. Other stateful hook authorization remains a hard authorization boundary in OMP: hook allow -> OMP allow; hook deny/unavailable -> OMP block. OMP yolo metadata does not bypass `missing_reservation`, `missing_claim`, `claim_conflict` denials, raw Bash/eval-tool blocks, or any stateful denial, and must not downgrade them to warnings or allow decisions.
- OMP built-ins that do not write repo files, including `ask`, `ast_grep`, `job`, `irc`, `task`, `todo`, `yield`, `report_tool_issue`, `generate_image`, and native read/search tools, are allowed by default. Other OMP-origin tools that are not built into the stateful classifier are recorded in `stateful tools list` and may be explicitly permitted with `stateful tools allow <tool>` for the enabled repo. This allowlist does not bypass hard-denied write or execution paths such as raw Bash, Python/JavaScript/JS/Ruby/Julia eval tools, or file writes without stateful authorization.
- In OMP, the extension uses the actual OMP session id (`event.sessionId` / `ctx.sessionManager.session.id`), stores it in `process.env.STATEFUL_SESSION_ID`, and the `stateful hook omp session-start` hook persists current-session files so MCP session-aware tools resolve the same OMP session. `state_session_register` -> `state_reservation_declare` -> `state_claim_acquire(paths=[...])` works from OMP current-session state without a manually pre-set env var.
- In stateful-bench DeNovo OMP runs, the adapter creates a per-instance OMP home instead of using the host default. `stateful:on` conditions install the OMP integration into that isolated home; Docker-backed stateful OMP runs use `/home/stateful` as the container runtime home so the mounted integration path is visible inside the agent. `stateful:off` / no-state conditions may still use the isolated OMP home but must not be treated as stateful sessions or repaired with Stateful MCP/sandbox guidance unless the benchmark prompt explicitly enables stateful.
- In OMP, never use raw Bash or Python/JavaScript/JS/Ruby/Julia eval tools for command-shaped work, including valid `stateful sandbox run` wrappers. Use `sandbox_bash` for read-only, write-targets, build, git, and github-pr sandbox profiles with the same profile flags, common sandbox flags, targets, reservation, and claim rules described below. Use `ext_ro_bash` for read-only `--fs external` commands with no write/create/directory scope. `ext_rw_bash` prompts for a scoped OMP UI grant unless `stateful.autoApprove: true` or per-call `auto_approve: true` is set; auto-approval skips only the Stateful-owned UI prompt and does not bypass Stateful sandbox scope validation, hooks, reservation/claim checks, or grant limits. For external writes or other external capabilities, absolute path-like scopes such as targets, directories, and sockets must be outside the repo, repo-relative write scopes require matching Stateful reservation and claims, and signal scope must be declared only when needed. Do not rely on OMP yolo/write approval for shell redirects, `cp`, `rm`, generators, raw eval snippets, raw git/test commands, or raw sandbox invocations.
- Generated OMP `sandbox_bash`, `ext_ro_bash`, and `ext_rw_bash` run sandbox commands in the background by default. With `async` omitted or `true`, they return a job id immediately, stream stdout/output via OMP messages using `pi.sendMessage`, and send final stdout, stderr, and exit status as a follow-up message. Set `async: false` to use the old awaited foreground behavior, where final stdout/stderr/status are returned in tool details. `ext_ro_bash` runs read-only external commands immediately without OMP UI confirmation. `ext_rw_bash` requires at least one `write_targets`, `create_targets`, or `write_dirs` entry. It prompts for a scoped purpose grant unless `stateful.autoApprove: true` or per-call `auto_approve: true` is set; auto-approval skips only the Stateful-owned UI prompt and does not bypass Stateful sandbox scope validation, hooks, reservation/claim checks, or grant limits. By default the grant covers up to five executions for ten minutes, and optional `grant_max_uses`, `grant_expires_seconds`, and `approval_examples` parameters can narrow or explain the grant. `ext_rw_bash` still passes the current command to the sandbox runner, but the approval prompt intentionally omits the raw command text. When auto-approval is enabled, no prompt is shown.
- Generated OMP sandbox tools expand unquoted, single-quoted, and double-quoted `skill://<name>` / `skill://<name>/<relative-path>` references in their `command` argument to files under the installed OMP agent `skills/` directory before executing the command; by default they spawn `stateful sandbox run`, but Docker-backed DeNovo OMP runs with `STATEFUL_OMP_SANDBOX=off` make `sandbox_bash` run directly inside the already isolated agent container. Unknown skills, query/hash suffixes, and traversal paths are rejected.
- Generated OMP extensions subscribe to the Stateful SSE notification stream after `session-start`. When a queued reservation becomes claimable, the extension injects a next-turn OMP message containing the `wait_id`, target action/path, and stored purpose; agents must still reread the target and call `state_reservation_claim` or rely on an authorized lazy-claim path before writing. Blocked OMP `edit` calls with safe repo-relative line targets are also stored as live-session lazy edit operations: wait-queue denials use the `wait_id`, while `missing_reservation` and `missing_claim` denials use a generated operation id.
- Reservation declarations are task-level file sets: one purpose should group every known file or directory the current task expects to touch. Declarations add to the session's active scope in that workspace, so expanding a task with a build/test directory or newly discovered source file does not remove earlier scopes. When adding targets, redeclare the active task scope before acquiring claims.
- Keep declared paths narrow inside the task file set; prefer exact files for edits, deletes, renames, and moves.
- Edit repo files using native edit tools with hook-visible targets, such as Codex `apply_patch` or Edit, after task-level reservation and successful same-session file claims covering each edited file.
- A directory claim for command-shaped artifact writes does not authorize native edits to individual files. For native edits, include each target file in the task reservation and claim the exact file path set before writing.
- Directory reservation and directory claims authorize only `write_directory` actions; any `write_file`, delete, rename, or move authorization requires exact file scope inside the task reservation and exact same-session file claims for every affected file path.
- Treat `tmp/` as disposable scratch space only. Anything under `tmp/` must be safe to delete at any time without breaking future work, handoff context, benchmark comparison, or review evidence. If an artifact must survive cleanup, create a separate purpose-named path and use exact `--write-target` / `--create-target` file scopes; when it should stay untracked, update `.gitignore` after declaring a reservation and acquiring a claim on that exact file.
- Use `<absolute-stateful-binary> sandbox run --fs write-targets --write-target <file> ... --command <cmd>` only for command-shaped writes that cannot be expressed as native edits, `--create-target <file>` for command-created files, and `--write-dir <repo-dir>` for command-shaped directory writes after task-level reservation covers that directory and a successful same-session directory claim matching the exact trailing-slashed directory passed to the sandbox. Repo `tmp/` has no special write-dir exemption; it is a normal repo path and still needs a matching claim. Use `--fs build --network enabled --write-dir <scratch-purpose>` for standard build/test commands; the build profile maps that purpose to `/tmp/stateful/<session>/<scratch-purpose>/`, sets standard temp variables under `/tmp/stateful/<session>/<scratch-purpose>/.stateful-tmp`, and sets Cargo output to `/tmp/stateful/<session>/<scratch-purpose>/target`. Configure non-Cargo tool caches and output directories under that external scratch root when they do not honor standard temp variables. The executable must be the trusted absolute `stateful` binary installed in the hook configuration; after rebuilding stateful itself, install the rebuilt binary to that trusted path before running commands that rely on new sandbox flags.
- Use `<absolute-stateful-binary> sandbox run --fs git --network disabled --command 'git <args>'` for local git operations and `--network enabled` only for networked git operations such as `fetch`, `pull`, or `push`. The git profile accepts a single `git ...` command, rejects explicit write targets, grants sandboxed write access to the repo worktree plus private transient git state, and protects persistent config/hooks while rejecting shell-dispatching options, path or exec overrides, inline/config-env config, disallowed subcommands such as `init` and `submodule`, branch upstream/tracking persistence, `push -u`, `rebase --exec`, grep pager dispatch, archive/fetch/push exec overrides, and config-mutating `git remote` subcommands such as `add`, `set-url`, `rename`, and `remove`.
- Use `<absolute-stateful-binary> sandbox run --fs github-pr --network enabled --command 'gh pr <list|view|status|create> ...'` for GitHub pull request inspection and creation. The profile accepts only one `gh pr` command, rejects explicit write targets, disables prompts, and denies browser/editor flags and PR mutation subcommands outside creation.
- Put nested benchmark run artifacts under `target/` when using `sandbox run-nested-codex-benchmark`. Hook authorization requires the installed trusted binary to be built with the `codex-benchmark` feature.
- For Docker-backed nested benchmarks, set `DOCKER_SOCKET` to an absolute Unix socket path and pass `--docker-socket "$DOCKER_SOCKET"` so only that Unix socket is exposed to the nested benchmark sandbox; the path must be absolute, exist, and be a Unix socket.
- Do not confuse Docker-backed nested benchmark sandboxing with DeNovo OMP agent Docker isolation. `sandbox run-nested-codex-benchmark --docker-socket ...` exposes only the Docker socket to the outer nested benchmark sandbox; stateful-bench DeNovo `--agent-docker-image` uses an adapter-owned image with Bun-installed `omp`, Linux `stateful`, and `bubblewrap` for generated OMP sandbox tools, mounts only the workspace, prompt file, and isolated OMP home into the agent container, and normalizes `$STATEFUL_HOME/config.yml` repo registry plus `repos/*.json` metadata paths to `/workspace`.
- Use `<absolute-stateful-binary> sandbox run --fs external --purpose <purpose> --command <cmd>` for approved external command execution. The external profile requires `--purpose` and `--command`, but it may be read-only with no declared write targets, create targets, write directories, sockets, or signal scope. When the operation writes outside the repo, add the needed `--write-target <absolute-external-path>`, `--create-target <absolute-external-path>`, or `--write-dir <absolute-external-dir>` scopes; absolute path scopes resolving inside the repo are rejected. When the operation writes inside the repo, use repo-relative target scopes and keep matching Stateful reservation plus same-session claims active before running it. It prompts for Codex approval when called directly in Codex and runs through the sandbox after approval. In OMP, call `ext_ro_bash` for read-only external commands with only `purpose` and `command`; it runs immediately without OMP UI confirmation. `ext_rw_bash` prompts for a scoped OMP UI grant unless `stateful.autoApprove: true` or per-call `auto_approve: true` is set; auto-approval skips only the Stateful-owned UI prompt and does not bypass Stateful sandbox scope validation, hooks, reservation/claim checks, or grant limits. The profile also supports `--connect-socket`, `--allow-signal`, and `--network` for approved external operations.
- Copying, exporting, syncing, or rehydrating a directory into a repo-external worktree is a write even when file bytes match the source. External worktrees such as `~/.config/superpowers/worktrees/...` still require the external sandbox approval boundary unless the operation stays inside an already approved sandbox profile. Filter local stateful artifact directories (`.codex`, `.stateful`, `.stateful_bench`, `.stateful_core`) out of exported workspaces unless the user explicitly approved copying them. For DeNovo benchmark workspace export and patch harvesting, also filter `upstream`.
- Re-read a file immediately before native edits, so preserve unrelated user changes.
- `apply_patch`, `Edit`, `Write`, and `file_change` are hook-authorized only when targets are visible to stateful policy. If denied, declare the missing exact scopes and acquire same-session file claims for those targets before retrying; use sandbox-run write targets only for command-shaped writes. In OMP, if an `edit` denial prints a queued lazy edit `operation_id`, fix the missing reservation/claim or wait for the reservation, then call `lazy_edit_resume` with that id instead of regenerating the same line-based patch.
- Native edit hooks and `sandbox run --fs write-targets` release their authorized same-session claims after the write transaction completes. If you need another edit after that boundary, reread the target and reacquire or let a claimable reservation lazy-claim at the next write boundary.
- In native Codex or OMP subagents, the active tool session is the session authority. Do not repair session identity with hook commands, shell environment overrides, or hook-state archaeology. If a native edit or write-target command is denied for missing reservation or same-session claim, use the same subagent session's Stateful MCP tools: `state_session_register` if needed, then `state_reservation_declare` and `state_claim_acquire(paths=[...])` for the exact path set. If the active tool list exposes only runtime-specific names, call the exact shown equivalent such as `mcp__stateful__state_reservation_declare` or `mcp__stateful_state_reservation_declare`.
- If a hook denies an action, read the denial and choose the documented alternative instead of retrying variants.

## Subagent Write Recovery

When a native Codex or OMP subagent hits `apply_patch writes require ... same-session file claim`, `Target is outside active reservation scope`, `missing_reservation`, `missing_claim`, `claim_conflict`, or `state_reservation_declare cannot resolve current stateful session`:

1. Stop retrying command variants; denials are the API.
2. Re-read the exact target if it exists.
3. Use MCP in this subagent session: `state_session_register` if needed, `state_reservation_declare(purpose=<task purpose>, files_planned=[...])` for the task's complete known file set, then `state_claim_acquire(paths=[...])` for the exact file path set being written. Use a one-item `paths` list for a single target when available; legacy `state_claim_acquire(path=...)` server requests remain accepted for single-path compatibility. If the active tool list exposes only runtime-specific tool names, call the exact shown equivalent such as `mcp__stateful__state_reservation_declare` or `mcp__stateful_state_reservation_declare`. For new files, add every exact new file path to the task reservation and claim those exact files, not only the parent directory. If the first recovery call returns `unsupported call`, stop and report the exact call name, active tool list if visible, and denial instead of retrying guessed variants.
4. Edit with native tools such as `apply_patch`, or use `sandbox run --fs write-targets` with the matching `--write-target` or `--create-target` for command-shaped writes.
5. If another session owns the claim, do not retry or steal it. Follow the wait queue when available; otherwise report the path, blocking session, and wait or reservation id to the parent agent.

For disposable repo `tmp/` directory claim conflicts, prefer a different session-unique scratch child over waiting when the artifact is truly disposable. A conflict on `tmp/<purpose>/` usually means another agent chose the same generic scratch name, not that the source-tree edit is blocked. Declare and claim a new child such as `tmp/<purpose>-<short-session-id>/`, then retry the command-shaped repo write with the exact same `--write-dir`. Build/test commands should use the build profile's external `/tmp/stateful` scratch instead of repo `tmp/`.

Do not diagnose these failures by running `stateful hook codex session-start`, `stateful hook omp session-start`, `stateful current`, `stateful notifications`, `stateful resume`, `strings <stateful>`, reading `$CODEX_HOME/shell_snapshots`, or manually setting `STATEFUL_SESSION_ID`. Those probes do not create the same-session claim required by hooks and usually waste the task budget.

For large source-tree reconstruction work, the parent agent must prove the write path before dispatching implementation subagents:

1. Build a concrete file manifest from the failing task and similar successful artifacts.
2. Declare a reservation and acquire a claim on the first exact file, then land a tiny native edit or command-shaped write.
3. Use a write smoke test before bulk delegation: either dispatch one subagent to prove an exact-file MCP write path, or require each implementation subagent to prove its first exact-file MCP write before receiving many files. Otherwise give them a narrow read-only research task.
4. Assign each subagent disjoint source files and disjoint scratch directories. The parent should not claim a broad source-tree directory or shared `tmp/upstream` directory and then ask subagents to write under it.
5. Do not send subagents CLI `reservation declare/request/claim` recipes to repair their session. Native subagents should use MCP tools; if MCP is missing or denied, they must report the exact denial and next file instead of probing session state.
6. Avoid reconstructing many files through large shell heredocs, `tee`, interactive stdin, or command-length experiments. Prefer native `apply_patch` after exact claims, or a verified git/network source through the git profile when that is available.

## Pick The Sandbox Profile First

Choose the narrowest existing entry point before writing the command. In Codex, the `Use` entries below are direct trusted `stateful sandbox run` wrappers through the configured absolute binary. In OMP, call `sandbox_bash` for the non-external `sandbox run --fs ...` profiles (`read-only`, `write-targets`, `build`, `git`, and `github-pr`), `ext_ro_bash` for read-only `--fs external` commands, and `ext_rw_bash` for `--fs external` commands with write/create/directory scope; raw Bash and Python/JavaScript/JS/Ruby/Julia eval tools are denied even if they contain the listed wrapper text.

| Need | Use | Do not use |
|------|-----|------------|
| Inspect files after native read/search tools are unavailable or insufficient | `sandbox run --fs read-only --network disabled` | raw Bash, eval tools, networked read-only |
| Inspect processes | `sandbox process find <selector>` | `ps`, `pgrep`, or process checks inside `sandbox run --command` |
| Read GitHub PR/Actions state that is outside the `github-pr` profile or needs general shell tooling | `sandbox run --fs external --network enabled --purpose <purpose> --command <cmd>`; in OMP use `ext_ro_bash` when the command is read-only | raw `git`, raw `gh`, mutating `git`/`gh`, browser/editor flows |
| Run any mutating `git ...` command, including PR preparation | `sandbox run --fs git --network disabled --command 'git <args>'` for local git, `--network enabled` only for remote git such as `fetch`, `pull`, or `push` | raw git, `write-targets`, `build`, or explicit write targets |
| Create GitHub pull requests | `sandbox run --fs github-pr --network enabled --command 'gh pr create ...'` for a single non-interactive create command; use the GitHub connector instead when explicitly allowlisted for the repo | raw `gh`, browser/editor PR flows, PR mutation subcommands outside creation, or explicit write targets |
| Run builds, tests, package managers, or generators whose outputs are disposable | `sandbox run --fs build --network enabled --write-dir <scratch-purpose> --command <cmd>`; scratch is created under `/tmp/stateful/<session>/<scratch-purpose>/` | raw test/build commands, repo `tmp` as build scratch, retained artifacts under `tmp/` |
| Run a non-git command-shaped repo write | `sandbox run --fs write-targets` with exact `--write-target`, `--create-target`, or narrow `--write-dir <repo-dir>` after matching reservation and same-session claim | native edits without a file claim, broad write dirs, git commands |
| Run nested Codex benchmark agents | `sandbox run-nested-codex-benchmark ...` | generic relaxed profiles or wrapping it inside another sandbox |
| Run a command outside the repo, including read-only/no-target external inspection or approved external writes | Codex: `sandbox run --fs external --purpose ... --command ...`, adding absolute external targets only when the operation needs declared external write/create/directory/socket/signal scope or repo-relative targets only when it needs Stateful-authorized repo writes. OMP: use `ext_ro_bash` for read-only external commands with only `purpose` and `command`; it runs immediately without OMP UI confirmation. `ext_rw_bash` prompts for a scoped OMP UI grant unless `stateful.autoApprove: true` or per-call `auto_approve: true` is set; auto-approval skips only the Stateful-owned UI prompt and does not bypass Stateful sandbox scope validation, hooks, reservation/claim checks, or grant limits before spawning the sandbox. | raw Bash, eval tools, or `write-targets` for repo-external writes |

PR workflows still use the git profile for git work: `status`, `diff`, `log`, `add`, `commit`, `switch`/`checkout`, `merge`, `rebase`, `tag`, and `push`. Do not use `--fs write-targets` just because git mutates the worktree or `.git`; the git profile owns that scope. GitHub pull request listing, viewing, status checks, and creation use the `github-pr` profile for `gh pr <list|view|status|create>`. Use `ext_ro_bash`/`--fs external` for read-only `gh` commands outside that narrow profile, such as Actions log inspection. If no listed profile matches the needed command, stop and report the exact unsupported command instead of trying raw Bash or a near-miss profile.

On macOS, read-only Go-based GitHub API commands such as `gh api` belong in that external path with `--network enabled` (OMP: `ext_ro_bash`) because the external Seatbelt profile permits the system identity/trust Mach lookups Go's TLS verifier needs for certificate validation. Do not use raw `gh`; add external write scopes only when the command actually writes.

## Tmp Retention Rule

`tmp/` means temporary. Store only cache files, test/build outputs, throwaway logs, and other artifacts that can disappear between commands. Do not put plans, notes, generated fixtures needed by later tasks, benchmark baselines, installable binaries, review evidence, or user-requested deliverables in `tmp/`.

If deleting the artifact would change future work, do not use `tmp/`. Create a narrow repo-relative path named for the purpose, use exact `--write-target` or `--create-target` file scopes for command-shaped writes, and add that path to `.gitignore` when the artifact should not be committed. Use `--write-dir <repo-dir>` only when the command genuinely needs directory-level repo writes, and keep that directory narrow, declared, and claimed. In parallel or subagent work, treat repo `tmp/<purpose>/` names as claimed resources, not shared workspaces; use unique children for each active session.

## Sandbox Examples

Examples assume `<absolute-stateful-binary>` is the trusted absolute binary installed in Codex hook configuration.

After changing sandbox command behavior in this repo, the user must bootstrap the trusted binary outside hook-mediated Bash before Codex can use new sandbox flags or new hook-authorized sandbox command forms such as `sandbox process find`:

```bash
cp target/debug/stateful <absolute-stateful-binary>
```

Read-only shell inspection fallback when native read/search tools are unavailable or insufficient:

```bash
<absolute-stateful-binary> sandbox run --fs read-only --network disabled --command 'rg auth crates'
<absolute-stateful-binary> sandbox process find --name python3 --contains denovo_codex_agent
<absolute-stateful-binary> sandbox process find --name stateful-bench --process-group <pgid>
```

Run a git operation:

```bash
<absolute-stateful-binary> sandbox run --fs git --network disabled --command 'git status --short'
<absolute-stateful-binary> sandbox run --fs git --network disabled --command 'git commit -m "Update command policy"'
<absolute-stateful-binary> sandbox run --fs git --network enabled --command 'git fetch --all'
<absolute-stateful-binary> sandbox run --fs git --network enabled --command 'git push origin HEAD'
```

Run a command-shaped write after task-level reservation covers the target and matching same-session claim is active:

```bash
<absolute-stateful-binary> sandbox run --fs write-targets --write-target docs/report.txt --command 'printf "%s\n" updated > docs/report.txt'
```

Create a command-generated file after task-level reservation covers the target and the matching same-session file claim is active:

```bash
<absolute-stateful-binary> sandbox run --fs write-targets --create-target reports/generated.txt --command 'printf "%s\n" notes > reports/generated.txt'
```

Run tests with a scratch purpose. Build outputs are disposable by policy because the build profile writes under `/tmp/stateful/<session>/<scratch-purpose>/`:

```bash
<absolute-stateful-binary> sandbox run --fs build --network enabled --write-dir test-run --command 'cargo test --workspace'
```

Run nested Codex benchmark agents only through the dedicated benchmark profile. This is not a general relaxed profile and must be the outermost sandbox command; do not wrap it inside another `stateful sandbox run`. It requires a trusted binary built with `codex-benchmark`, `--purpose`, `--write-dir target`, `--codex-home-root target/...`, and exactly one `--command`. The profile enables network, grants write access only under the `target/` artifact tree and the nested Codex home root under `target/`, and sets `STATEFUL_NESTED_CODEX_HOME_ROOT` so benchmark launchers can create per-agent `HOME`, `CODEX_HOME`, and XDG directories there. This command is currently supported only on macOS; Linux support needs a separately verified profile.

```bash
<absolute-stateful-binary> sandbox run-nested-codex-benchmark --purpose "run nested Codex chaos benchmark" --write-dir target --codex-home-root target/nested-codex-homes/run-1 --timeout-seconds 120 --command '<benchmark-command>'
```

Run a read-only repo-external command with no declared write scope. Codex prompts on `sandbox run --fs external --purpose ... --command ...`; OMP uses `ext_ro_bash`, which runs immediately without OMP UI confirmation:

```bash
<absolute-stateful-binary> sandbox run --fs external --purpose "inspect external config" --command 'test -r "$HOME/.config/example/config.toml" && wc -l "$HOME/.config/example/config.toml"'
```

Request a repo-external write by adding absolute external write scope. In OMP, use `ext_rw_bash` with at least one write target, create target, or write directory scope. It prompts for a scoped OMP UI grant unless `stateful.autoApprove: true` or per-call `auto_approve: true` is set; auto-approval skips only the Stateful-owned UI prompt and does not bypass Stateful sandbox scope validation, hooks, reservation/claim checks, or grant limits. The prompt lists the purpose, declared write/socket/signal scope, network mode, limits, and examples rather than the raw command text. Matching later calls reuse the grant until its max uses or expiry is reached, then prompt again. When auto-approval is enabled, no prompt is shown:

```bash
<absolute-stateful-binary> sandbox run --fs external --purpose "install rebuilt stateful binaries" --write-dir <external-install-dir> --command 'install -m 755 target/release/stateful <external-install-dir>/stateful'
```

`stateful sandbox run --fs write-targets` targets must be repo-relative. Do not target `.git`, symlinks, paths outside the repo, or paths with control characters. Use `--write-target` for existing files, `--create-target` for new files, and `--write-dir <repo-dir>` only after including the trailing-slashed directory scope in the task reservation, such as `reports/generated/` or `tmp/reports/`, and acquiring the same-session directory claim before using that `--write-dir`. Repo `tmp/` is not special for write-targets; it follows the same claim and safety rules as any other repo directory. Use `--fs external --purpose <purpose> --command <cmd>` for approved external operations. A read-only external command may omit declared scopes; absolute write targets, create targets, write directories, connected sockets, and signal permission are optional approval details when needed and must resolve outside the repo. Repo-relative external write scopes require matching Stateful reservation and claims. Use `--fs build --write-dir <scratch-purpose>` for standard build/test commands; the scratch root is `/tmp/stateful/<session>/<scratch-purpose>/`, not repo `tmp/`. The read-only profile always requires `--network disabled`. Process inspection must use `stateful sandbox process find`; raw `ps` and `pgrep` inside `sandbox run --command` are disallowed. The git profile manages repo write scope itself; do not pass write targets with `--fs git`, and do not use it for config-mutating remote setup such as `git remote add` or `git remote set-url`. `/dev/null` is writable inside the sandbox; do not declare it as a target. `stateful sandbox run` is macOS-first and release-verified with Seatbelt. Linux bubblewrap support is implemented but experimental until verified in a Linux release environment.

## Prefer

- MCP or native read tools for search and inspection when available.
- Codex: `<absolute-stateful-binary> sandbox run --fs read-only --network disabled --command <cmd>` only as the fallback for Bash-tool command-shaped read-only inspection when native read/search tools are unavailable or insufficient. OMP: use native tools first, then `sandbox_bash` with `--fs read-only --network disabled` for repo read-only fallback commands, or `ext_ro_bash` for read-only external shell commands.
- `<absolute-stateful-binary> sandbox process find --contains <literal>` or `--name <comm>` with optional `--pid`, `--parent-pid`, or `--process-group` selectors for process checks.
- Codex: `<absolute-stateful-binary> sandbox run --fs write-targets ... --command ...` for Bash-tool command-shaped writes that need a real shell, can be limited to exact file targets, create targets, or a narrow claimed repo directory, and have matching reservation plus a same-session claim. OMP: use `sandbox_bash` with the same write-targets flags after matching reservation and claim.
- Codex: `<absolute-stateful-binary> sandbox run --fs build --network enabled --write-dir <scratch-purpose> --command 'cargo test --workspace'` for build or test commands that write disposable build artifacts under `/tmp/stateful/<session>/<scratch-purpose>/`. OMP: use `sandbox_bash` with the same build profile flags.
- Codex: `<absolute-stateful-binary> sandbox run --fs git --network disabled --command 'git <args>'` for local git operations such as status, diff, log, add, commit, checkout, restore, reset, merge, rebase, and clean; use `--network enabled` for fetch, pull, push, and other remote git operations. OMP: use `sandbox_bash` with the same git profile flags. Remote metadata mutation such as `git remote add` and `git remote set-url` is rejected.
- Codex: `<absolute-stateful-binary> sandbox run --fs github-pr --network enabled --command 'gh pr <list|view|status|create> ...'` for non-interactive GitHub pull request listing, viewing, status checks, and creation; OMP: use `sandbox_bash` with the same github-pr profile flags. Use the GitHub connector instead when explicitly allowlisted for the repo.
- `<absolute-stateful-binary> sandbox run-nested-codex-benchmark --purpose ... --write-dir target --codex-home-root target/... --command ...` for nested Codex benchmark runs that need network and isolated per-agent Codex homes under `target/`.
- Codex: `<absolute-stateful-binary> sandbox run --fs external --purpose ... --command ...` for approved sandboxed command execution outside the repo, with no declared write scope for read-only operations, absolute external scopes only when needed, and repo-relative scopes only for Stateful-authorized repo writes. OMP: use `ext_ro_bash` for read-only external commands with only `purpose` and `command`; it runs immediately without OMP UI confirmation. `ext_rw_bash` prompts for a reusable scoped purpose grant unless `stateful.autoApprove: true` or per-call `auto_approve: true` is set; auto-approval skips only the Stateful-owned UI prompt and does not bypass Stateful sandbox scope validation, hooks, reservation/claim checks, or grant limits before invoking this profile internally. `sandbox_bash` rejects `--fs external`.
- Stateful diagnostics through MCP tools, native tools, or sandbox-run wrappers through the trusted absolute `stateful` binary.

## Avoid In Bash Or Eval Tools

- Codex raw Bash is denied by stateful hooks, including namespaced runtime aliases whose leaf tool is `bash` such as `functions.bash`; use a sandbox-run wrapper through the trusted absolute `stateful` binary or MCP/native tools instead. OMP raw Bash and Python/JavaScript/JS/Ruby/Julia eval-tool execution are always denied, including aliases whose leaf tool is `bash`, `python`, `javascript`, `js`, `ruby`, or `julia`, and including commands that invoke a valid `stateful sandbox run` wrapper. Namespaced read/search aliases follow their leaf tool and remain native read/search tools. Raw read-only Bash and eval snippets are also denied for repo-internal commands such as `rg`, `git status`, `sed`, or quick language snippets; in OMP use native read/search tools, `sandbox_bash`, `ext_ro_bash`, or `ext_rw_bash`.
- Outer shell wrappers around the sandbox command: environment assignments, command substitution, outer redirects, outer pipelines, multiple commands, duplicate `--command`, or an untrusted executable path.
- Session-repair probes such as `stateful hook codex session-start`, `stateful hook omp session-start`, `stateful current`, `stateful notifications`, `stateful resume`, `stateful reservation declare/request/claim`, `strings <stateful>`, `$CODEX_HOME/shell_snapshots`, or outer `STATEFUL_SESSION_ID=...` assignments to force a claim. Use MCP session, reservation, and claim tools instead.
- Shell write syntax outside a sandbox-run `--command`: `>`, `>>`, heredocs, and `| tee`.
- Direct file mutation: `rm`, `mv`, `cp`, `mkdir`, `touch`, `chmod`, `chown`.
- Raw process inspection such as `ps`, `pgrep`, `ps auxww`, `ps -ef`, `ps -eo pid,args`, or `ps e...` inside `sandbox run --command`; use `stateful sandbox process find` instead.
- Any generator, formatter, package manager, or script that creates, updates, deletes, or moves repo files.
- Storing anything in `tmp/` that must survive cleanup or be available to later work; use exact retained file targets in a purpose-named path and `.gitignore` as needed.
- `sandbox run --fs read-only --network enabled`; the read-only profile rejects network access.
- `sandbox run --fs build` without exactly one `--write-dir <scratch-purpose>`, with repo `tmp/...` as that scratch purpose, or with explicit `--write-target` / `--create-target`.
- Raw git commands; use `sandbox run --fs git --network disabled` for local git operations and `--network enabled` only for remote git operations.
- Raw test commands; use `sandbox run --fs build --network enabled --write-dir <scratch-purpose>` for commands that write disposable build or test artifacts.
- Generic relaxed sandbox profiles for nested Codex. Use only `sandbox run-nested-codex-benchmark`; it is intentionally narrower than a reusable relaxed profile.
- Most `stateful` control commands through Bash; use MCP tools when available.
- Repo-external writes through repo-internal profiles such as `--fs write-targets`; use `sandbox run --fs external --purpose ...` in Codex or `ext_rw_bash` in OMP so the approval prompt shows the external write scope, purpose, grant limits, and examples rather than the raw command text before execution. `stateful.autoApprove: true` or per-call `auto_approve: true` skips only that Stateful-owned prompt while sandbox scope validation, hooks, reservation/claim checks, and grant limits still apply. When auto-approval is enabled, no prompt is shown.

## If Blocked

- Do not retry the same command with small variations.
- If the denial asks for scope, add the missing exact file or directory scopes to the task reservation, acquire exact same-session claims for those targets with `state_claim_acquire(paths=[...])` when several paths are missing, then use native edit tools with hook-visible targets for repo changes.
- If `state_claim_acquire` reports `claim_conflict`, do not retry the claim acquisition. To wait for the path, call `state_reservation_request` with a stable `request_id`, the denied `action`, `path`, and `purpose`; then poll `state_notifications_poll` or `state_resume_next` for the reservation. When reserved, reread the target. Native edit hooks and `sandbox run --fs write-targets` can lazy-claim the reservation at the next write attempt; manual MCP/CLI flows should call `state_reservation_claim` with the `wait_id` before retrying.
- If a denial includes `wait_id`, `queue_position`, or reservation guidance, follow that wait queue protocol: poll `state_notifications_poll` / `state_resume_next`, reread the target after reservation, then either retry the native/sandbox write so the write boundary lazy-claims it, or call `state_reservation_claim` first for manual MCP/CLI flows.
- If raw Bash or eval-tool execution is blocked, choose MCP/native inspection first and native edit tools after task-level reservation covers the target plus a successful same-session file claim for repo edits. In Codex, use `<absolute-stateful-binary> sandbox run --fs read-only --network disabled` only as the read-only shell/Python fallback, `<absolute-stateful-binary> sandbox run --fs write-targets` for command-shaped writes after matching reservation and same-session claim, or `<absolute-stateful-binary> sandbox run --fs git` for git operations. In OMP, use `sandbox_bash` for read-only, write-targets, build, git, and github-pr sandbox profiles, `ext_ro_bash` for read-only `--fs external`, or `ext_rw_bash` for external commands with write/create/directory scope.
- If repo-external command execution is needed, use `<absolute-stateful-binary> sandbox run --fs external --purpose ... --command ...` for the Codex approval prompt. In OMP, use `ext_ro_bash` for read-only external commands with only `purpose` and `command` and no OMP UI confirmation. `ext_rw_bash` prompts for a scoped OMP UI grant unless `stateful.autoApprove: true` or per-call `auto_approve: true` is set; auto-approval skips only the Stateful-owned UI prompt and does not bypass Stateful sandbox scope validation, hooks, reservation/claim checks, or grant limits. Add absolute external targets, directories, sockets, or signal permission only when the operation needs that external scope; repo-relative write targets, create targets, and write dirs require matching Stateful reservation and claims. `sandbox_bash` rejects `--fs external`, and raw OMP Bash/eval-tool external sandbox calls are denied. Do not try to bypass the external profile with raw `cp`, `install`, `cargo install`, shell redirection, or repo-internal sandbox profiles.
- If a denial mentions a stateful MCP coordination tool, prefer that MCP tool in Codex sessions.
- If a denial says the running server does not support sandbox write directories, restart the stateful server with a binary that supports sandbox write-directory authorization, then retry after rereading and reacquiring the needed claim.
- If `run-nested-codex-benchmark` is denied for missing feature support, install or rebuild the trusted binary with the `codex-benchmark` feature before retrying.
- If MCP tools are unavailable, do not try `stateful mcp call` through a read-only network-enabled sandbox; the read-only profile requires network disabled and most stateful control commands are not hook-approved raw Bash.
- If no policy-compliant path is available, report the exact command and denial reason.
